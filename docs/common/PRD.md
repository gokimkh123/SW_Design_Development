## 1. 요약

- **서비스 개요**
  - 생활 설문 · 상황 질문 기반 사용자 **생활 페르소나(AI 분신)** 생성
  - 후보 룸메이트 AI와 **가상 7일 · 생활 장면 20개** 동거 시뮬레이션 수행
  - 결과 기반 **궁합 점수 · 시뮬레이션 리포트 · 생활 규칙 초안** 제공
  - 입주 후 **AI 중재**를 통한 갈등 조기 해소
- **대상**: 대학 기숙사 2인실 입사생(1차), 코리빙 · 셰어하우스 입주 청년(2차), 생활관 관리자(B2B, 최종)
- **차별점**: 설문 점수 비교가 아닌 **생활 장면 시뮬레이션 기반 궁합 검증**, 매칭 이후 **규칙 합의 및 중재까지 연계**
- **11/3 발표회 목표**: 방문객의 부스 내 직접 체험 — 생활 페르소나 생성 → 시드 후보 3명과의 가상 동거 관람 → 생활 규칙 초안 확인 (흐름 A → B → C). 흐름 D(입주 후 관리)는 최종 개발 범위
- **개발 기간**: **6일(10/27 ~ 11/1)**. 범위를 P0 · P1 · P2로 구분하여 P0만으로 시연이 완결되도록 설계

### 2.2 해결할 문제

| ID | 문제 | 현황 |
| --- | --- | --- |
| P1 | 입주 전 궁합 확인 불가 | 설문 점수 비교만으로는 "새벽 통화", "친구 초대" 등 실제 장면에서의 반응 예측 불가 |
| P2 | 생활 규칙 부재 | 입주 초기 규칙 합의 없이 생활 시작, 갈등 발생 후에야 기준 차이 인지 |
| P3 | 갈등 표현 · 중재 수단 부족 | 직접 언급 부담으로 불만 누적, 관리자 중재는 민원 접수 후 사후 대응 위주 |

### 2.3 기존 방식과의 비교

| 서비스·방식 | 제공 기능 | 한계 |
| --- | --- | --- |
| 대학 생활관 배정 (다수) | 무작위 · 선착순 · 학과 기준 배정 | 생활 습관 미반영 |
| 조선대 AI 매칭 (2026 시범) | 생활 습관 설문 기반 자동 매칭 | 실제 상황 반응 · 대화 방식 미반영 |
| Roome · RoomSync (해외) | 선호도 기반 매칭, 공과금 분할 | 국내 미지원, 입주 후 관리 부재 |
| 커뮤니티 게시판 | 자기소개 글 기반 개인 탐색 | 검증 · 매칭 기능 부재 |

### 2.4 기술 근거

- Stanford · Google 연구(Park et al., 2024): 1,052명의 인터뷰 · 설문 데이터 기반 개인별 생성형 에이전트 생성 및 응답 재현도 측정
- 인터뷰 + 설문 결합 시 재현도 **86%** (설문만 82%, 인구통계만 74%) → 생활 설문 + 상황 질문 결합 페르소나 설계의 근거
- 단, 시뮬레이션 결과는 **예측치**이며 최종 선택은 당사자가 결정

## 3. 목표와 성공 지표

### 3.1 발표회(11/3) 목표

| ID | 목표 |
| --- | --- |
| G1 | 12문항 응답 기반 3분 이내 생활 페르소나 카드 생성 |
| G2 | 두 페르소나 간 생활 장면 20개 실제 LLM 대화 시뮬레이션 및 장면별 원만 · 조율 · 충돌 판정 |
| G3 | 시뮬레이션 결과 기반 궁합 점수 · 리포트 · 생활 규칙 초안(6개 영역) 자동 생성 |
| G4 | 방문객의 페르소나 생성 ~ 생활 규칙 확인 전 과정 단독 수행 가능 |
| G5 | 발표회 5시간 서비스 무중단 운영 |

### 3.2 발표회 범위 밖 (Non-goals)

- 실제 학교 메일 인증, 실사용자 간 매칭 (방문객은 시드 후보와만 매칭)
- 흐름 D의 우리 방 · 체크인 · 관리자 화면, 공용품 정산, 학사 일정 연동
- 결제 · 수익 모델 구현, 네이티브 앱 배포, 실제 학생 개인정보 수집

## 5. 핵심 개념과 용어

| 용어 | 정의 |
| --- | --- |
| 생활 페르소나 | 설문 · 상황 질문 응답 기반 사용자 생활 프로필. 5개 축 점수, 유형명, 대화 방식, 꼭 지켜줘 · 괜찮아요 항목으로 구성 |
| AI 분신 | 생활 페르소나를 시스템 프롬프트로 갖는 LLM 에이전트. 시뮬레이션 내 사용자 대리 발화 |
| 5개 축 | 수면 리듬(아침형↔올빼미) · 청결 · 소음 민감 · 사교성 · 공유 관대. 각 0~100 |
| 대화 방식 | 상황 질문 기반 갈등 대응 스타일: 직설(`direct`) · 회피(`avoid`) · 지연(`delay`) |
| 가상 동거 | 두 AI 분신의 가상 7일 · 생활 장면 20개 공동 경험 시뮬레이션 |
| 생활 장면 | 갈등 유형 기반 상황 템플릿 (예: 3일차 수요일 01:10, 심야 게임) |
| 판정 | 장면 결과 분류. **원만**(`harmonious`): 이견 없음 · **조율**(`negotiated`): 이견 후 대화로 합의 · **충돌**(`conflict`): 합의 실패, 판정자의 합의안 제안 |
| 궁합 점수 | 장면 판정 분포 기반 0~100 점수 (참고 정보, 매칭은 양측 수락으로 성립) |
| 생활 규칙 | 시뮬레이션 합의 내용의 6개 영역(조용한 시간 · 친구 초대 · 청소 · 냉장고 · 냉난방 · 공용품) 정리본 |
| AI 중재자 | 규칙 수정 제안 · 불편 메모를 두 페르소나 기준으로 검토하여 중재안 · 요청형 문장을 생성하는 LLM 기능 |
| 리플레이 모드 | 사전 생성 시뮬레이션 결과의 실시간 재생 모드. 교수 설명용 및 장애 대비용 |
| 생활 지수 | 규칙 이행률 · 체크인 기반 방 단위 지표 (최종 범위) |

## 8. 시뮬레이션 엔진 설계

- 백엔드와의 함수 인터페이스: [API 명세서 7장](API.md#7-엔진-인터페이스) 참고

### 8.1 실행 흐름

```mermaid

    autonumber
    participant FE as 프론트엔드
    participant API as 백엔드
    participant MOD as 진행자
    participant A as 내 AI
    participant B as 후보 AI

    FE->>API: 시뮬레이션 시작 (페르소나, 후보)

    FE->>API: 진행 상황 구독 (SSE)
```

### 8.5 궁합 점수와 한 줄 판정

```text
궁합 점수 = round(100 × (원만 수 + 0.5 × 조율 수) / 판정된 장면 수)
```

- `round`는 사사오입(0.5 올림) 기준

- 기획서 예시(원만 16 · 조율 3 · 충돌 1) 적용 시 87.5 → **88점** (기획서 리포트 화면과 일치)
- 판정 보류 장면은 분모에서 제외

| 점수 | 한 줄 판정 |
| --- | --- |
| 85 이상 | 함께 살기 무난한 조합이에요 |
| 70 ~ 84 | 몇 가지만 맞추면 잘 지낼 수 있어요 |
| 50 ~ 69 | 미리 규칙을 꼭 정해 두는 게 좋아요 |
| 50 미만 | 생활 방식 차이가 커요 |

- 한 줄 판정 문구는 앱 화면 노출용 문구이므로 구어체 유지

### 8.6 LLM 선택과 비용

| 항목 | 결정 |
| --- | --- |
| 모델 | **Claude Haiku 5.5** (`claude-haiku-5-5`). 현 Claude 모델 중 최저가 (100만 토큰당 입력 $0.10 · 출력 $0.50, 프롬프트 10만 토큰 이하 기준) |
| 호출 설정 | 에이전트 발화: effort `low`(짧고 빠른 응답), 판정: 구조화 출력(JSON 스키마) |
| 교체 가능성 | `engine/llm.py`의 `LLMClient` 단일 지점 교체로 무료 API 등 타 모델 전환 가능 |
| 무료 API 미채택 사유 | 무료 API의 낮은 분당 요청 한도. 방문객 1명당 약 300회 호출로 부스 동시 이용 시 차단 위험 큼 |
| 예상 비용 | 호출 1회 입력 1,200 · 출력 300 토큰 가정 시 방문객 1명(후보 3명 × 20장면) 약 $0.08 ~ 0.10. 방문객 100명 + 개발 테스트 합계 $30 이내 예상 |
| 키 관리 | 팀원 배포 없음. 실제 키는 VM `~/roommate/.env`에만 저장, 로컬 개발은 가짜 엔진(`ENGINE_IMPL=fake`). 실제 엔진 테스트 시 건한이 사용 한도를 건 개인별 키 발급 후 폐기, Console 사용 한도 설정 |

| --- | --- |
| 동시 실행 | `LLM_MAX_CONCURRENCY` 기반 동시 요청 수 제한. 후보 3명 병렬, 후보 내 장면은 순차 실행 |
| 실패 처리 | 호출 실패 시 2회 재시도, 재실패 시 해당 장면 "판정 보류"(`pending`) 처리 후 다음 장면 진행 |
| 시연 안전장치 | 리플레이 모드, `single` 모드 전환 |
| 품질 확인 | 골든 페어 2쌍(하늘-수빈: 수면 충돌 다수, 하늘-다은: 원만) 기반 프롬프트 변경 시마다 결과 확인 |
| 안전 | 에이전트 프롬프트 내 비하 · 혐오 표현 금지, 성별 · 출신 지역 등 민감 정보의 매칭 기준 제외 |

### 부록 C. 계산 규칙 (초안)

**5개 축 (0~100)**

| 축 | 계산 | 이름표 |
| --- | --- | --- |
| 수면 리듬 | q01 취침 시각 21:00 → 0, 03:00 → 100 (선형, 범위 밖은 0 또는 100) | 0~33 아침형 · 34~66 중간형 · 67~100 올빼미 |
| 소음 민감 | q02 둔감 0 · 보통 33 · 예민 67 · 아주 예민 100 | 선택지 그대로 |
| 청결 | q04 · q05 평균 (부지런한 선택지부터 100 · 67 · 33 · 0) | 0~24 낮음 · 25~74 보통 · 75~100 높음 |
| 사교성 | q07 각자 조용히 0 · 필요할 때만 33 · 가끔 수다 67 · 친구처럼 100 | 0~24 낮음 · 25~74 보통 · 75~100 높음 |
| 공유 관대 | q08 전부 각자 0 · 공용품만 33 · 물어보고 67 · 자유롭게 100 | 0~24 낮음 · 25~74 보통 · 75~100 높음 |

- **대화 방식**: q09 ~ q12 최빈 방식, 동점 시 q09 방식 적용
- **후보 1차 점수**

```text
1차 점수 = round(100 − Σ 가중치 × |나의 축 값 − 후보의 축 값|)   ※ round는 사사오입
가중치: 수면 리듬 0.3 · 소음 민감 0.25 · 청결 0.2 · 사교성 0.15 · 공유 관대 0.1
```
